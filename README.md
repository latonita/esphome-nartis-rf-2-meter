**Нартис RF433-2 (Д101-2)**

# esphome-nartis-rf-2-meter

Чтение счётчиков электроэнергии **Нартис И100/И300/И500** (выпуска примерно с 2024 г.)
по радиоканалу 443 МГц. ESP32 с радиомодулем CMT2300A **эмулирует выносной дисплей
НАРТИС-Д101-2** и получает от счётчика показания.

Для работы требуется серийный номер счётчика.

Счетчики Нартис, комплектуемые Д101-2 — вероятно, построены на китайской платформе **Wasion** и 
поверх радиоканала используют протокол из Поднебесной - **DL/T 645-1997**.
Компонент реализует базовый DL/T 645-1997 и читает заранее настроенные страницы показаний. 
Произвольный параметр, отсутствующий в таблице, запросить нельзя.

В природе замечены дисплеи Д101-2 2025 года выпуска, которые начинают с единичного запроса 
в формате **DL/T 645-2007**, но далее продолжают по-старому.

> **Компонент экспериментальный** 🙈 Проверен на живых счётчиках, но на отдельных моделях 
> и годах выпуска могут быть несостыковки. Обратная связь приветствуется.

# Что можно прочитать

В зависимости от модели и настройки счётчика доступны:

**Энергия (нарастающим итогом)**
- активная энергия, импорт: всего, тариф 1, тариф 2 (а также тарифы 3/4 и значения
  на конец прошлого расчётного периода)
- активная энергия, экспорт: всего, тариф 1, тариф 2

**Мгновенные значения** (только на многофункциональных счётчиках)
- напряжение по фазам A/B/C
- ток по фазам A/B/C и ток нейтрали
- активная мощность
- частота сети
- температура

**Служебное**
- часы счётчика (дата и время)
- текущий тариф и число тарифов

Полный рабочий пример со всеми этими сущностями —
[`example_esp32.yaml`](example_esp32.yaml).

Что именно пришлёт ваш счётчик, зависит от его набора индикации (настраивается
конфигуратором «Nartis Tools»). Сущность, для которой счётчик не прислал значение,
просто остаётся без данных — на остальные это не влияет.

# Аппаратное обеспечение

Нужны ESP32 и радиомодуль **CMT2300A**. Модуль управляется программным 3-проводным
SPI, аппаратный `spi:` не нужен.

| Сигнал | Назначение |
| --- | --- |
| `pin_sdio` | данные SPI (двунаправленный MOSI/MISO) |
| `pin_sclk` | тактовый сигнал SPI |
| `pin_csb`  | выбор чипа (регистры) |
| `pin_fcsb` | выбор чипа (FIFO) |
| `pin_gpio3`| сигнал прерывания (INT2) — **обязателен** |

# Быстрый старт

```yaml
external_components:
  - source: github://latonita/esphome-nartis-rf-2-meter
    components: [nartis_rf_2_meter]
    refresh: 1s

nartis_rf_2_meter:
  id: nartis
  address: "123456789012"    # 12 цифр с шильдика счётчика
  pin_sdio: GPIO19
  pin_sclk: GPIO18
  pin_csb: GPIO5
  pin_fcsb: GPIO21
  pin_gpio3: GPIO22
  update_interval: 300s

sensor:
  - platform: nartis_rf_2_meter
    name: "Активная энергия, всего"
    tag: 0x00
    unit_of_measurement: kWh
    accuracy_decimals: 3
    device_class: energy
    state_class: total_increasing
    filters: [multiply: 0.001]   # значение приходит в Вт·ч

text_sensor:
  - platform: nartis_rf_2_meter
    name: "Часы счётчика"
    tag: 0x29

binary_sensor:
  - platform: nartis_rf_2_meter
    name: "Последний опрос успешен"
```

# Конфигурация хаба

| Параметр | Обяз. | По умолчанию | Описание |
| --- | --- | --- | --- |
| `id` | да | — | идентификатор компонента |
| `address` | да | — | серийный номер счётчика, ровно 12 цифр с шильдика |
| `pin_sdio` / `pin_sclk` / `pin_csb` / `pin_fcsb` / `pin_gpio3` | да | — | подключение CMT2300A |
| `update_interval` | нет | `300s` | период опроса |
| `frequency` | нет | из `address` | принудительная частота канала. Обычно не нужна |
| `data_page` | нет | `auto` | какой набор параметров запрашивать: `auto`, `0xF200` (энергия и часы) или `0xF202` (то же плюс мгновенные значения) |
| `request_gap` | нет | `500ms` | пауза между запросами |
| `rf_rx_timeout` | нет | `1500ms` | сколько ждать ответа за одну попытку |
| `rf_retries` | нет | `2` | повторов запроса при потере связи (0–10). Всего попыток = `1 + rf_retries` |
| `rx_center_offset` | нет | `758` | подстройка частоты приёма в кодах CMT2300A (1 код ≈ 6.2 Гц). Менять только при проблемах со связью |

**О периоде опроса.** Штатный дисплей синхронизируется со счётчиком примерно раз в
час, и сам счётчик обновляет показания не чаще. Опрашивать намного чаще смысла нет.
Значение по умолчанию `300s` — разумный компромисс.

**О частоте.** На данный момент частота вычисляется по серийному номеру. Вычисленная частота
печатается в лог при старте. Если расчет неверный, то можно задать вручную.

**О `data_page`.** По умолчанию (`auto`) компонент сам выбирает набор данных по тому,
какие сущности вы описали: если нужны мгновенные значения — запрашивает расширенный
набор, иначе — обычный. Задавать вручную имеет смысл, только если счётчик на
расширенный набор не отвечает.

# Сенсоры

У каждого сенсора задаётся **ровно один** из двух ключей:

- `tag` — параметр из показаний счётчика, см. [таблицу ниже](#таблица-параметров-tag);
- `status` — служебное значение: `active_tariff` (текущий тариф), `tariff_count`
  (число тарифов) или `temperature` (температура).

Плюс все стандартные параметры ESPHome (`name`, `unit_of_measurement`,
`device_class`, `state_class`, `filters`, `icon`, `entity_category`, …).

**Значения публикуются «как есть»**, без пересчёта — множитель задаётся фильтром
`multiply` прямо в YAML, чтобы в конфигурации было видно, в чём измеряется сущность.
Нужные множители — в таблице.

## Числовой сенсор (sensor)

Любой `tag`, кроме `0x29` (часы — только текстом), либо `status`.

```yaml
sensor:
  - platform: nartis_rf_2_meter
    name: "Напряжение фазы A"
    tag: 0x15
    unit_of_measurement: V
    accuracy_decimals: 1
    device_class: voltage
    state_class: measurement
    filters: [multiply: 0.1]
```

## Текстовый сенсор (text_sensor)

Любой `tag`, включая `0x29` — часы счётчика публикуются строкой вида
`2026-07-17 15:54:58`.

```yaml
text_sensor:
  - platform: nartis_rf_2_meter
    name: "Часы счётчика"
    tag: 0x29
    icon: mdi:clock-outline
    entity_category: diagnostic
```

## Бинарный сенсор (binary_sensor)

Одна диагностическая сущность: `true`, если последний цикл опроса получил всё, что
запрашивал. Ключей выбора нет — сенсор всего один.

```yaml
binary_sensor:
  - platform: nartis_rf_2_meter
    name: "Последний опрос успешен"
```

По умолчанию `device_class: connectivity` и `entity_category: diagnostic`; оба можно
переопределить.

Зачем это нужно: на неудачном цикле остальные сущности **ничего не публикуют** и
сохраняют предыдущее значение. Отличить свежие данные от многочасовых по самому
значению невозможно — этот сенсор говорит об этом прямо. Цикл считается успешным,
только если получены **все** нужные данные.

# Таблица параметров (TAG)

`tag` — номер параметра в списке индикации счётчика.

| TAG | Параметр | Фильтр | Единица |
| --- | --- | --- | --- |
| `0x00` | Активная энергия, импорт, всего | `multiply: 0.001` | кВт·ч |
| `0x01` / `0x02` | Активная энергия, импорт, тариф 1 / тариф 2 | `multiply: 0.001` | кВт·ч |
| `0x03` / `0x04` | Активная энергия, импорт, тариф 3 / тариф 4 | `multiply: 0.001` | кВт·ч |
| `0x05` | Активная энергия, экспорт, всего | `multiply: 0.001` | кВт·ч |
| `0x06` / `0x07` | Активная энергия, экспорт, тариф 1 / тариф 2 | `multiply: 0.001` | кВт·ч |
| `0x08`–`0x13` | Прочие регистры энергии (реактивная и т.п.) | `multiply: 0.001` | кВт·ч / квар·ч |
| `0x14` | Напряжение (однофазный счётчик) | `multiply: 0.1` | В |
| `0x15` / `0x16` / `0x17` | Напряжение фаз A / B / C | `multiply: 0.1` | В |
| `0x18`–`0x1A` | Линейное напряжение AB / BC / CA | `multiply: 0.1` | В |
| `0x1B` | Ток (однофазный счётчик) | `multiply: 0.01` | А |
| `0x1C` | Ток нейтрали | `multiply: 0.01` | А |
| `0x1D` / `0x1E` / `0x1F` | Ток фаз A / B / C | `multiply: 0.01` | А |
| `0x20` | Активная мощность, сумма | `multiply: 10` | Вт |
| `0x21`–`0x23` | Активная мощность фаз A / B / C | `multiply: 10` | Вт |
| `0x24`–`0x27` | Реактивная мощность, сумма и по фазам | `multiply: 10` | вар |
| `0x28` | Частота сети | `multiply: 0.01` | Гц |
| `0x29` | Дата и время счётчика | — | только `text_sensor` |
| `0x2A` | Температура | `multiply: 0.1` | °C |
| `0x2C`–`0x3F` | Те же регистры энергии на конец прошлого расчётного периода | `multiply: 0.001` | кВт·ч |

Проверены на живом счётчике: энергия (`0x00`–`0x02`, `0x05`–`0x07`), напряжения
`0x15`–`0x17`, токи `0x1C`–`0x1E`, мощность `0x20`, частота `0x28`, часы `0x29`.
Остальные строки — по аналогии с соседними параметрами того же типа; при первой
публикации такого параметра в лог выводится однократное предупреждение. Проверьте,
что значение осмысленное, и, если что-то не сходится, — сообщите.

# Диагностика и советы

- **Счётчик не отвечает.** Проверьте `address` (12 цифр с шильдика) и частоту,
  напечатанную в логе при старте. Затем попробуйте подстроить `rx_center_offset`:
  ответ счётчика приходит на несколько кГц выше нашей передачи, и приёмник надо
  навести на него.
- **Мало данных.** Счётчик присылает только то, что настроено в его наборе
  индикации. Если нужных параметров нет, компонент напишет об этом в лог.
- **`Previous cycle still running`.** `update_interval` меньше, чем время цикла с
  повторами. Увеличьте интервал или уменьшите `rf_retries`.
- **Подробный лог.** При `level: DEBUG` в лог пишутся все переданные и принятые
  кадры, уровень сигнала (RSSI) и разбор по параметрам:

  ```
  [D][nartis_rf_2_meter]: RX [46] rssi=-96 dBm: 29.00.01.28.68.XX.XX.XX.XX...
  [D][nartis_rf_2_meter]:   TAG 0x00 [4] = 35.4B.C9.00 (13191989 Wh)
  [D][nartis_rf_2_meter]:   TAG 0x29 [7] = 58.54.15.05.17.07.26 (2026-07-17 15:54:58)
  ```

  Поставьте `logger: tx_buffer_size: 1024`, иначе длинные строки обрезаются.
- **Самопроверка.** Компонент сверяет `сумма == Тариф 1 + Тариф 2` и предупреждает
  при расхождении — такое сообщение означает ошибку разбора, а не странность
  счётчика.
